# workflow-mm:契约驱动多模型工作流(harness 无关)

把一个已确认的开发目标,经"模型选择 → 计划 → 派发 → 验收 → 报告"跑完。
设计目标是宿主无关:只依赖每个 coding agent 都有的四样能力——读写文件、跑 shell 命令、向用户提问、(可选)子代理机制。没有实时可视化面板,过程状态全部落盘到文件,这也是断点续跑的依据。

## 与家族 skill 的关系

宿主装有 `planner` / `local-executor` 时,对应阶段按它们的细节执行;本文件的内嵌版本保证没有它们也能跑通。验收原则来自工作流约定:验收命令由工具执行、交叉验收、同一错误最多一次带新证据的重试。

## 流程总览

第一问(模型选择) → 计划(契约) → 用户批准 → 逐包"生成 → 落盘 → 验收" → 汇总报告。

## 阶段 0:模型选择(第一问)

用户点名 workflow 后、做任何事之前,问一次,三选一:

1. **默认会话模型(推荐)**:生成动作由当前会话的模型承担,不经本地。
2. **默认本地模型**:全部生成动作路由到 llama-mm 的默认档(`~/.llama-mm/profiles.json` 顶层 `default` 指向的档位)。
3. **列出本地 route**:读 profiles.json(或 MCP `list_profiles`),向用户列出全部档位供挑选:档位名、tier(quality/bulk)、端口、模型、本地还是远程。

规则:

- 选择写入契约的"执行分派"维度,全程不改;中途要换,停下问用户。
- 此选择只决定"生成动作路由到哪",不改变子代理的宿主模型(harness 支持给子代理指定模型时可作为增强,不作依赖)。
- 未跑本 skill 的宿主模块(如批处理脚本)不适用此问;它们的路由在各自配置里。

## 阶段 1:计划(契约)

与用户确认目标后,产出 `task-contract.md`,9 个维度(与 planner 一致):

1. 目标与范围:做什么、不做什么。
2. 接口契约:接口签名、数据结构及直接调用方。
3. 接线矩阵:组件间调用关系与依赖方向。
4. 环境约束:运行环境事实与限制条件。
5. 启动/构建命令。
6. 验收命令:最窄验证命令、预期输出、失败停止条件。
7. 执行分派:依赖顺序、可并行拆分;**写入阶段 0 的模型选择结果**,每个任务包标注执行档位。
8. 执行任务包:每包唯一目标文件、允许修改范围、需读取的文件与符号片段、显式排除项、回传 schema(默认"结论/依据/待办",依据须 file:line 出证);结果要进入后续任务上下文的包应标注。
9. 阻塞项与残余风险。

硬规则:

- 一包只允许一个可编辑目标文件;跨文件变更拆成多包。
- 不把完整契约或整个仓库交给执行者;只给该包需要的局部片段。
- 契约落盘后请用户批准;批准前不执行任何落实动作。

## 阶段 2:派发执行

按契约任务包逐个执行,一次一个文件,落盘立即跑该包验收命令。

**路径一:宿主有子代理机制**(Agent/Task 类工具)

- 每包派一个新子代理,prompt = 该包契约原文 + 执行指令模板。
- 选了本地档位时,指令模板要求子代理把代码生成经 llama-mm 交给指定档位(接口见下节),子代理自己负责拆解规格、校验回传、落盘;子代理调不到 MCP 时退化为 HTTP。
- 终验子代理必须是没见过该包生成过程的新子代理,给它契约原文 + 生成差异。

**路径二:宿主无子代理机制**(如 Codex)

- 主上下文按 local-executor 契约模式内嵌派发:把任务包规格经 llama-mm 发给执行档位,拿回代码,主上下文校验、落盘、跑验收命令。
- 生成与验收同处一个上下文时,验收重点放在命令输出与契约逐条对照,弥补上下文同源的盲区。

上下文预算(硬约束):单次读取 ≤300 行或 12000 字符;每包引用 ≤5 个文件片段;搜索结果 ≤50 条;日志 ≤200 行。

## llama-mm 接口(按可用性取用)

1. **MCP 工具**(首选,宿主注册了 llama-multimodel-mcp 时):`list_profiles` 列档位;`chat` / `complete` 用 `profile_id` 指定档位,发任务包规格,收生成结果。注意:不少宿主对单次 MCP 调用有 ~30 秒硬上限,本地大模型整文件生成经常超;超时不代表模型不可用,立即退 HTTP。
2. **HTTP 直连**(兜底,也是长生成的实际主力):每个档位是一个 llama-server 实例,`POST http://127.0.0.1:{port}/v1/chat/completions`(OpenAI 兼容,x99 远程档同此形态);端口与模型名读 `~/.llama-mm/profiles.json`;curl 超时给到 300 秒。
3. **CLI**:`chat` 没有通用命令行,不要去找;判定类问题(阻塞分诊、保留/丢弃、验收争议)可用 `llama-decide` / `llama-decide-batch`(与 MCP `decide` / `decide_batch` 同源)。

## 阶段 3:验收与重试

- 验收命令由工具执行,以退出码为准;不接受"已完成"但没有命令输出的报告。
- 打回修复必须附契约原文 + 差异(失败命令的输出)。
- 同一错误最多一次带新证据的重试;再失败标记 BLOCKED,跳过继续,最后统一上报。
- 全部包完成后做一次跨文件终验:全量构建/测试命令 + 对照契约维度逐条核查。

## 阶段 4:状态与报告

每完成一个包(或遇到阻塞)立即更新 `workflow-state.md`(与契约同目录);这是断点续跑的唯一依据,格式:

```markdown
# workflow-state
- goal: <一句话目标>
- contract: task-contract.md
- routing: <阶段 0 的选择,如 "option-3 profile=gemma4-12b">
- updated: <YYYY-MM-DD HH:MM>
- packages:
  - P1 <名称>: done | tier: quality | 验收: <命令> → exit 0 | <完成时刻>
  - P2 <名称>: in-progress | tier: quality | 备注: <卡在哪>
  - P3 <名称>: blocked(重试 1 次) | 失败: <输出摘录 ≤5 行>
- uncovered: <哪些没做、为什么>
```

结束报告必须包含:各包状态与验收证据、模型路由记录(哪些包走了哪个档)、阻塞项、未覆盖部分。

中断续跑:读 `workflow-state.md` 与 `task-contract.md`,跳过 done 的包继续;`workflow-state.md` 在但契约文件丢失时无法续跑(任务包片段只在契约里),报告后重开;blocked 项需用户决策后重开。

## 已验证(2026-09-26,qwen35-4b 真实派发)

- 全流程通过:契约 → 两包真实派发(21-31s/包)→ pytest 退出码验收 → 状态落盘,终验 10/10 exit 0。
- 打回重试路径实测两轮:第 1 轮模型语义偏差,带 diff 重试修正;第 2 轮暴露契约自相矛盾(重试语义与验收夹具冲突),按编排者职责修契约后通过。教训:打回重试的失败输出要对照夹具复核,规格冲突时修契约而非重问模型。
- 点名档位路由(阶段 0 选项 3)与换档决策(12B 档在 3.5GB 空闲显存下降到 1.4t/s,用户决策换 4B 档 `-ngl 0`)有记录可回溯。
- 中断续跑通过:状态文件写 P1 done / P2 in-progress,重开后跳过 P1 续做 P2,状态往返一致。
- 环境注意:宿主 MCP 单次调用 30 秒上限会掐断长生成,HTTP 直连是长生成的实际主力(接口节已更新)。
