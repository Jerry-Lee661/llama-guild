# 参考基线（Reference Baseline）

> 以下数据来自开发者的实际调参档案（硬件级别描述，无个人路径信息），
> 目的不是刷分，而是证明这套工作流的档位划分有真实硬件依据：
> **quality 档与 bulk 档的速度/质量权衡是实测出来的，不是拍脑袋。**

## 硬件

- 单卡 24GB RDNA3 消费级 GPU（Vulkan 后端），16C/32T 移动级 CPU，~46GB 内存
- llama.cpp server（b10xxx nightly，含 MTP 投机解码与 router 模式）
- 全部档位 `-ngl 99` 全量上卡，KV cache q4_0/q8_0 量化

## 档位实测（27-35B 级本地模型）

| 档位角色 | 规模/形态 | 实测解码速度 | 备注 |
|---|---|---|---|
| quality（执行档） | 27B dense Q4 + MTP n=3-4 | 46-62 t/s（64k-128k 窗口） | 跨文件接线/配置生成质量可靠；`-ub 512` 是本机 Vulkan 的决定性参数（>512 触发慢路径 16-24 t/s） |
| bulk（批量档） | 35B MoE Q4 + MTP n=3-4 | 120-140 t/s（长上下文） | 代码质量弱于 dense，适合机械批量 |
| bulk（另一例） | 35B MoE + MTP n=4 | ~205 t/s（短上下文） | 高速但质量进一步让步 |
| 规划层参照 | 云端强模型 | — | 只出契约不写码 |

## 关键调参结论（对任何 24GB 级单卡可复用）

1. **MTP 投机解码**：n-max 甜蜜点 3-4；`--no-spec-draft-backend-sampling` 必加
   （否则后端采样回退 CPU，负优化）
2. **KV 量化**：q4_0 ≈ 0.04 MB/token 级（dense）/ 架构相关波动大，启动后看日志核对
3. **显存预算**：24GB 卡留 4GB 边际 → 同一时刻只容一个 27-35B 大盘；
   这是工作流"分组降本、一次编排每档位至多一次加载"的物理依据
4. **长上下文**：64k-128k 可用；超过窗口甜蜜点掉速明显，契约的任务包设计
   （≤5 片段）正是为了避免把上下文灌满
5. **投机解码验收率**是档位健康度信号：acceptance 掉到 <0.3 通常意味着
   上下文超窗或草稿头与目标不匹配——`complete` 工具的 draft 遥测直接可读

## 复现

任意 24GB 单卡 + llama.cpp server（b11xx+）可复现量级。把你的实测填进
profiles.json 的 description，`bench` 工具可直接产出同格式数据。
