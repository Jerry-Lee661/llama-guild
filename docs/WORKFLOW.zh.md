# 契约驱动多模型工作流 — 方法论

> 版本 1.0 · 本文是整个仓库的理论基础；工具与配置都只是这套方法论的载体。

## 1. 为什么需要这套工作流（实证背景）

某真实项目由本地 27B 模型一次性产出，验收时发现 **6 个致命缺陷 + 7 个严重问题**。
复盘确认：**不是模型"笨"，而是工作流缺了契约约束 + 工具化验收。**

本地（及一切中小）模型的五类失败模式（全部来自实测）：

| 模式 | 实例 | 对策 |
|------|------|------|
| ① 低层拼写/记忆错误 | 幻觉包名、参数写反、语法碎片 | 喂参考资料禁回忆；改完立即语法验证 |
| ② 写了但没接线（死代码） | 组件写对却从未启动 | 规划层给出"接线矩阵"；执行后契约核对 |
| ③ 接口契约断裂 | 端点对不上、路径重复前缀 | 规划层写死接口契约 |
| ④ 环境错位 | 容器内的命令目标却是宿主 | 固化环境事实 |
| ⑤ 依赖缺失 | 代码调用未安装的 CLI | 验证依赖存在 |

**核心结论：中小模型是合格的"填空执行者"，不是"自驱工程师"。**
- ✅ 做得好：理解架构方向、按模板填空、安全参数落实
- ❌ 做不好：精确回忆、跨文件自由接线、运行环境特判

因此：**强模型/人类负责"规划与纠错"，本地模型负责"执行"，验收交给工具。**
大模型只读一次项目产出契约，迭代循环全部落在便宜模型上——这就是省钱的方式。

## 2. 模型分档

配置在 `profiles.json`，用 `tier` 字段固定为两档执行角色：

| tier | 定位 | 适合 | 不适合 |
|------|------|------|--------|
| `quality` | 高质量执行档 | 代码实现、跨文件接线、系统配置生成、排障 | 高速批量 |
| `bulk` | 高速批量档 | 机械填空、模板套用、重命名/格式化、翻译注释 | 需要质量的实现 |

（规划层不在 profiles 里——它由云端强模型或人类担任。）

决策要点：
- 速度焦虑的本质是**验证循环慢** → 把验收自动化，迭代成本趋近 0
- 参考硬数据：开源 32B 级模型 SWE-bench 约 40%；给本地模型"自由探索仓库"的任务注定失败，给它"契约 + 片段填空"则完全可用
- 量化（Q4 级）是质量甜点位；不要让 bulk 档做 agentic 工具调用

## 3. 三层工作流：规划 → 落实 → 验收

### 3.1 规划层（强模型/人类）— 产出**契约**而非意图
产出 `task-contract.md`（9 维度）：目标与范围 / 接口契约 / 接线矩阵 / 环境约束 /
启动构建命令 / 验收命令 / 执行分派建议 / 执行任务包 / 阻塞项与残余风险。

关键纪律：一个执行任务只允许一个目标文件；接口必须给局部参考片段，
不把"模型自己探索"当契约；未确认事实标 `[NEEDS VERIFICATION]`。

### 3.2 落实层（本地模型 + 执行者）— 一次只改一个文件
- 上下文输入 = 该子任务的最小任务包（目标文件 + 接口契约 + ≤5 参考片段 + 窄验证命令）
- 改完立即跑验证；连续失败 3 次停止
- 系统级操作（装依赖/改配置/起服务/接插件）**在范围内**：本地模型生成命令与配置，
  执行者应用并验证——不要以"任务复杂/涉及真实工具"为由跳过本地派发

### 3.3 验收层（工具/编排者/人类）— **绝不交给产出代码的模型**

| 层 | 手段 | 拦截 |
|----|------|------|
| L0 语法 | py_compile / node --check / json / yaml | ① |
| L1 契约扫描 | 对照接线矩阵与接口契约（每端点有实现、无重复前缀） | ②③ |
| L2 构建 | 项目构建命令 | ①⑤ |
| L3 集成冒烟 | 启动 + 端到端验证 | ②③ |
| L4 环境核对 | 运行环境特判（路径、平台命令差异） | ④ |

**闭环：** 规划契约 → 单文件落实 → 立即验收 → 打回（附契约原文+差异）→ 再修 → 通过。

## 4. 上下文预算管理

工具层硬限制（写入所有角色提示词）：

```
单次读取   ≤ 300 行 / 12000 字符（带路径+行号，超限截断可续读）
文件片段   ≤ 5 个 / 子任务
搜索结果   ≤ 50 条
日志       ≤ 200 行
```

原则：
- 不让 agent 自由探索仓库 → 先定位再读取、假设驱动检索
- prompt 里"省着点读"挡不住工具返回几万行 → 限制放在工具/规程层
- 不追求大上下文，追求"永远用不满"

## 5. 路由策略（编排层硬规则）

1. **清单制派发**：契约"执行任务包"清单上的子任务一律派发给本地执行子agent；
   派发与否机械判定，禁止"任务复杂/系统级/不是填空"等主观跳过理由
2. **tier 映射**：quality 档接高质量落实，bulk 档接高速批量；契约可覆盖
3. **主模型自查**：发现自己在写契约内目标文件 → 停下改为派发
4. **分组降本**：同档位任务连续派发，一次会话每档位至多一次加载-卸载循环
5. **例外收紧**：仅 `LOCAL_MODEL_FAILED` 连续 3 次或用户明确要求时才可接管，接管前报告
6. **宽执行模式（无契约轻派发）**：资料整理、信息提取、内容替换改写、简单工具调用四类机械任务，无需契约即可派发给本地执行者（文本任务走 bulk 档、工具调用走 quality 档）；边界是不产出业务实现代码、输入单次 ≤24K tokens、多步依赖仍需契约。宽执行把"本地模型只在正式契约里用"扩展为"日常杂务也落在本地"，判定保持类型白名单的机械性，不做主观扩围。

> **社区实证（2026-09，lcz.me「一个Agent两个大语言模型」讨论）**：多位实践者独立得出相同结论——
> 用 skill / agent.md 约束模型行为，"前几次服从，之后就会时不时绕过规范"；删减工具也不够。
> 有效做法是**机械式闸门**：把强制条件定义成可自动判定的检查（如"资安问题必须附前沿模型
> 检核证据，否则不许 commit"），没通过就物理挡下。本项目的清单制派发、provider 特性门控、
> VRAM 预算守护都是这一原则的实现。同帖也指出多模型协作最费心思的是"信息搬运"——
> 契约任务包（最小包 + 结构化回传）正是对这一痛点的工程化。

## 6. 与现有项目的关系

- [github/spec-kit](https://github.com/spec-kit)：规格驱动流程。本项目与其互补——spec-kit 管"规格"，
  本项目管"让本地模型执行规格"（spec-kit 社区正在手工做的强/弱模型分工，见其 discussion #1784）
- [llama-swap](https://github.com/mostlygeek/llama-swap)：模型热切换代理。可作为本项目 openai-compatible
  provider 的后端；但 llama-swap 没有工作流层（契约/路由/验收）
- BYOK 插件（如 lmstudio-copilot-provider）：解决"模型接入"，本项目解决"模型分工"
